# backend/services/.module_map.md

## Service Groups

- Camera domain:
  - `cameraService.js`: CRUD, import/export, restore, delivery normalization, bulk area operations, read-model caching.
  - `cameraSourceLifecycleService.js`: source/IP/codec/transport/enabled update classification, MediaMTX refresh orchestration, runtime reconnecting state, stream revision bumps, and masked lifecycle event writes.
  - `cameraHealthService.js`: probe scheduling, runtime health scoring, online/offline transitions, recording/thumbnail coordination.
  - `cameraHealthPolicy.js`: pure external health policy resolution + `guardProbeSettlement` (deadline-race so one never-settling probe rejects instead of freezing the whole sweep — the 2026-08-17 fleet-health freeze). Root cause lives in `rtspProbe.js` (`close` listener on the fresh-socket fallback).
  - `cameraMonitoringAlertPolicy.js`: pure Telegram monitoring alert policy for opt-in strict internal HLS monitoring eligibility and online/offline transition detection.
  - `telegramAlertConfirmationPolicy.js`: pure Telegram alert confirmation timing policy that delays DOWN/UP sends until monitored state remains stable.
  - `cameraRuntimeStateService.js`: runtime state persistence and signal tracking. Also maintains the dead-at-source streak (`camera_runtime_state.source_dead_since/_reason`) because every health outcome funnels through `upsertRuntimeState` — a caller-side version would drift the first time a probe path was missed. Stored as UTC ISO, unlike the app-local `updated_at`, because it is subtracted from a clock.
  - `cameraReactionService.js`: anonymous one-vote-per-device verdict on a camera (`camera_reactions`, PK on `(camera_id, device_hash)` — the primary key IS the one-vote rule). Community-only, and an unknown id answers identically to a hidden one so the endpoint is not an existence oracle. `getPublicSummary` returns BOTH totals plus the caller's own vote — the owner overruled a likes-only first cut on 2026-08-02 so the page reports what visitors actually said; `getAdminSummary` LEFT JOINs from `cameras` so unrated cameras are listed too (an inner join would make a sample of three look like the whole fleet) and returns `{cameras, totals}` ranked worst-first, unrated last.
  - `cameraReportService.js`: categorised per-camera reports from anonymous visitors (`camera_reports`), 5/hour/device, community-only. Free text is safe here ONLY because nothing written is ever rendered on a public surface — it goes to the admin queue and the Telegram feedback chat. `occurred_at` is what makes it more than a complaint box: a coordinate into the recording archive. Never expose the queue publicly or it becomes the comment wall this design avoids. `listReports` filters by status/category/camera and pages, with `status: 'open'` meaning "not finished"; its `summary` is computed over the WHOLE table even under a filter, so narrowing the view cannot hide how much is left.
  - `cameraSourceDeadPolicy.js`: pure rule for "offline" vs "GONE" — only `stream_ended` / `http_404` / `http_410` count, and only after `CAMERA_SOURCE_DEAD_CONFIRM_HOURS` (default 6). 403 is excluded on purpose: `data.bojonegorokab.go.id` answers 403 to any client without a browser User-Agent.
  - `cameraSourceHealthService.js`: staff-only read model of confirmed dead sources behind `GET /api/admin/cameras/source-health`. Separate from the camera list because `CAMERA_RUNTIME_STATE_PROJECTION` is shared with both PUBLIC read models, so a column there would ship fault detail to anonymous visitors.
  - `rtspProbe.js`: self-contained RTSP DESCRIBE reachability probe (digest/basic auth), extracted from cameraHealthService; `probeRtspSource` re-exported there.
  - `cameraImportHelpers.js`: pure bulk-import helpers + `IMPORT_*` config consts, extracted from cameraService.
- Billing / rental / access domain (revenue + tenancy — deep rules in `docs/billing-rental.md`):
  - `cameraAccessService.js`: single live-access decision point (30s cached); gates non-community cameras on every surface.
  - `billingService.js`: admin camera→customer assignment, daily idempotent prorated charges, suspend/resume, orphan-heal.
  - `walletService.js`: prepaid wallet ledger + idempotent charge refs (money = INTEGER rupiah, never float).
  - `paymentService.js`: `manual`/`midtrans`/`ipaymu` drivers, exactly-once crediting (unsigned callbacks re-query the API).
  - `paymentSettingsService.js`: admin-editable gateway config (DB→env→default); secrets write-only.
  - `billingPlanService.js`: plan catalog, per-account state, trial window, registration approval.
  - `customerCameraService.js` / `customerCameraIpService.js`: customer self add/edit/delete bounded by plan; RTSP URL policy.
- Voucher domain (per-area time-gated live access):
  - `voucherService.js` / `voucherOrderService.js` / `voucherPass.js` / `voucherPublicService.js`: voucher issue/redeem/order/public-claim flow.
- Streaming domain:
  - `mediaMtxService.js`: MediaMTX path sync and API interaction, plus the ingest circuit breaker (`reconcileParkedIngest`, every 2 min): a camera dead >30 min is demoted to `sourceOnDemand` so MediaMTX stops dialling it forever — on the `RtpRtspFlyer` firmware that endless retry is what KEEPS a wedged camera wedged. Decision is pure in `utils/internalIngestPolicy.js#shouldParkInternalIngest`, which refuses to park anything while health itself looks stale (a frozen sweep must not be able to park the fleet). Kill switch `MEDIAMTX_PARK_DEAD_INGEST=off`.
  - `streamService.js`: stream URL/status operations.
  - `streamWarmer.js`: proactive stream warmup.
  - `hlsProxyService.js`: internal/external HLS proxy library (trusted-proxy/CIDR, rate limiter, session store, SSRF guard) behind the thin `routes/hlsProxyRoutes.js`.
  - `externalStreamProxyService.js`: stateful SWR/dedup external-stream proxy plugin behind a thin re-export route.
- Recording domain:
  - Facade & top-level orchestration:
    - `recordingService.js`: thin facade exposing `startRecording`, `stopRecording`, `restartRecording`, `reconcileRecordingLifecycle(All)`, `autoStartRecordings`, `adoptExistingRecordings`, `getRecordingStatus`, `getStorageUsage`, `attachScheduler`, `initializeBackgroundWork`, `shutdown`. Internals delegate to focused services; do not add new responsibilities here. `shutdown()` DETACHES recorders by default (they keep running across the restart and the next boot adopts them); pass `{ stopRecorders: true }` only when the box itself is going down and nothing will come back for them.
  - Paths, intervals & policy (pure):
    - `recordingPaths.js`: single source of truth for `RECORDINGS_BASE_PATH` (ENV override via `RECORDINGS_DIR`). Every recording service reads from here.
    - `recordingIntervalsPolicy.js`: every interval, threshold, batch size, and cooldown for the recording domain. ENV-overridable knobs: `RECORDING_SCHEDULED_CLEANUP_INTERVAL_MS`, `RECORDING_RECOVERY_MAX_CONCURRENT`, `RECORDING_EMERGENCY_DISK_THRESHOLD_BYTES`, `RECORDING_EMERGENCY_DISK_TARGET_BYTES`.
    - `recordingLifecyclePolicy.js`: pure desired-state decision (start / stop_offline / stop_disabled / stop_unrecordable / wait_cooldown / noop_*).
    - `recordingPartialRecoveryPolicy.js`: pure retry/quarantine decision for recovery. Partials are never terminal-quarantined, but they DO go `retain_dormant` past `RECORDING_RECOVERY_PARTIAL_MAX_ATTEMPTS` (12) — file untouched and still owned by retention, it just stops being re-enqueued. Without that cap, "never quarantine" meant "retry forever" and 1,693 dead partials starved fresh segments out of all 3 recovery slots for 2 hours, stalling playback as well as the archive.
    - `recordingPathSafetyPolicy.js`: pure path/filename/byte-range safety shared by playback, cleanup, recovery.
    - `recordingSegmentFilePolicy.js`: pure path/name classifier for final/partial/temp + `resolveSegmentSource(basePath, cameraId, filename) → { sourceType, sourcePath, finalFilename }`.
    - `recordingTimePolicy.js` / `recordingProcessTimePolicy.js`: app-timezone filename parsing and FFmpeg `TZ` env.
    - `recordingRetentionPolicy.js`: retention window + safe-filename + per-file delete decision (re-exports intervals constants for back-compat).
    - `recordingFailureClassifier.js`: classify FFmpeg exit into operator-meaningful lifecycle/failure reasons.
  - Lifecycle & process control:
    - `recordingLifecycleReconciler.js`: DB/process desired-state safety net. Single source for start/stop/`stop_disabled`/`stop_unrecordable` transitions; called by health monitor tick, `autoStartRecordings`, `updateRecordingSettings`, and `cameraHealthService` online/offline transitions.
    - `recordingProcessManager.js`: FFmpeg start/stop/restart serialization. Owns spawn + graceful kill, plus `adopt()` (track a recorder we did not spawn — pid only, liveness polled via `kill(pid,0)` since there is no `close` event) and `detachAll()` (release our side and LEAVE ffmpeg running — the server-shutdown path). Signals go through `signalRecord()`, which targets the pid, never the negated process group.
    - `recordingRuntimeState.js`: in-memory FFmpeg process state.
    - `recordingHealthMonitor.js`: per-camera stream health (data freshness, cooldown, suspend reason, restart-on-freeze). An offline->online transition clears the failure COUNT as well as the cooldown: those failures were caused by the outage, and a rebooted camera that is not serving RTSP yet on attempt #1 would otherwise wait 5 minutes for attempt #2. A camera that pings but sends no frames never transitions, so the breaker still engages for it. Owns the 5s tick loop. Internal cross-method calls go through a late-binding `api` object so `vi.spyOn` works.
    - `recordingStarter.js`: pure builder for `sourceConfig`, `ffmpegArgs`, `spawnOptions`, `stderrLogPath`, and camera/pending directories. `prepareRecordingStart({ camera, recordingsBasePath })` returns a struct the facade hands to `recordingProcessManager.start()`. Sets `detached: true` — recorders run in their own process group so a backend restart cannot signal them. The fMP4 flags go through `-segment_format_options`, NOT a bare `-movflags`: at top level the segment muxer drops them silently and the mp4 muxer holds the whole moov in memory until the segment closes (measured: 48 bytes on disk after 12s vs 236 KB, and every abrupt stop destroyed the entire in-flight segment).
    - `recordingFfmpegLog.js`: per-camera ffmpeg stderr log (`<base>/cameraN/ffmpeg.log`) + tailer. FFmpeg's stderr goes to this FILE instead of a pipe to the backend — a pipe to a dead parent kills the recorder on its next write, which is why "spawn detached" alone is not enough. The tailer replays new bytes into the same `onStderr` path as before (freshness, `segment_completed`, error classification all unchanged), supports `fromEnd` for adoption, and self-truncates past `FFMPEG_LOG_MAX_BYTES` (8 MB) so progress spam cannot fill the recordings disk.
    - `recordingDomainBootstrap.js`: the domain's start/stop sequence, shared by `server.js` (single-process mode) and `recorder.js` (worker mode) so the boot order cannot drift. That order is load-bearing: adoption MUST precede auto-start, or a camera whose recorder survived gets a second ffmpeg on the same output directory.
    - `recordingControlService.js`: the ONLY way API-side code asks for recording work. In single-process mode it calls `recordingService` directly; in worker mode it queues a `recording_reconcile_requests` row and reads runtime status from what the worker published. Call sites (`cameraService`, `cameraHealthService`, `recordingPlaybackService`) go through here so exactly one module knows which process owns recording. Reports `status: 'unknown'` (never `'stopped'`) when the worker heartbeat is stale — claiming "not recording" for a camera we simply cannot see invites a double-start.
    - `recordingWorkerStateRepository.js`: the DB interface between the two processes — `recording_process_state` (worker's runtime map, mirrored for the API), `recording_health_snapshot` (dashboard payload + worker heartbeat), `recording_reconcile_requests` (work queue, coalesced per camera and deleted once claimed). Every call degrades to "unknown" rather than throwing; none of it is worth failing an API request over.
    - `recordingAdopter.js`: boot-time hand-off. Scans for recorders left by the previous instance and re-attaches them via `recordingProcessManager.adopt()` instead of killing them, then hands the adopted pids to the reaper as `keepPids`. Deliberately does NOT re-implement "should this camera be recording?" — it adopts anything whose camera row exists and lets the lifecycle reconciler (which runs right after) stop what it must, cleanly. Only recorders for deleted cameras are retired here.
    - `recordingStderrParser.js`: pure FFmpeg stderr line classifier (`segment_completed` / `segment_debug` / `error` / `other`).
    - `recordingAudioFallback.js`: in-memory, per-camera "this camera's advertised audio cannot actually be recorded". `-map 0:a?` in `recordingStarter.js` already adapts to cameras that declare NO audio; this covers the ones that declare it and never send it — camera 1169 publishes `pcm_alaw` in its SDP and delivers no audio packet over its mandatory UDP transport, so FFmpeg buffered video waiting to interleave and exited in 8s having written nothing. `recordingService.handleRecordingClosed` marks the camera when the exit classifies as `audio_stream_stalled`/`unsupported_track_codec`, and the next start is video-only. Deliberately NOT persisted: re-testing once per boot costs one failed start and lets a camera that starts delivering audio recover on its own, where a DB column would go stale the way `cameras.video_codec` did.
    - `recordingAutoStarter.js`: one-shot boot auto-start. Pre-marks offline cameras as suspended, then delegates to lifecycle reconciler. Runs AFTER `recordingAdopter`, so already-adopted cameras are seen as recording and are not given a second ffmpeg.
    - `recordingOrphanReaper.js`: discovery (`scanRecordingProcesses` → `[{pid, cameraId}]`) plus selective retirement. `reapStrayRecordingProcesses({ keepPids })` signals only recorders NOT claimed by adoption, and goes SIGINT-first (ffmpeg finalizes the segment) with SIGKILL reserved for whatever ignores it. It used to `kill -9` everything it found at boot; that is what turned every restart's in-flight segment into a "moov atom not found" file.
  - Segments, recovery, repositories:
    - `recordingSegmentFinalizer.js`: idempotent finalization pipeline (validate duration → remux to temp → atomic promote → DB upsert → cleanup source). `drain(timeoutMs)` loops until in-flight is empty or deadline hits.
    - `recordingRecoveryService.js`: bounded recovery queue with single public entrypoint `enqueueRecovery(input) → Promise<result>`. `recoverNow` is no longer exported — every caller respects `maxConcurrent`. Owns `isFileOwned()` (the only in-progress tracker in the recording domain).
    - `recordingRecoveryScanner.js`: non-destructive folder scan for pending partials and final orphans. Exposes `scanOnce()` + `intervalMs`; scheduling is owned by the maintenance coordinator.
    - `recordingSegmentRepository.js`: duplicate-safe `(camera_id, filename)` persistence.
    - `recordingRecoveryDiagnosticsRepository.js`: operator-visible recovery states. `incrementAttempt` runs UPSERT+SELECT in a transaction so attempt_count reads are deterministic under concurrency.
  - Maintenance, cleanup, disk:
    - `recordingMaintenanceCoordinator.js`: owns lazy creation of `recordingRecoveryScanner`, `recordingBackgroundCleanupService`, `recordingEmergencyDiskService`. `registerSchedulerTasks(scheduler)` registers all 5 maintenance loops; `startLegacyTimers()` is the test-only manual scheduling fallback. Uses late-binding `api` object for spy compatibility.
    - `recordingCleanupService.js`: bounded per-camera cleanup + emergency cleanup. Owns per-camera concurrency lock AND rate-limit (`minIntervalMs`, default 60s). `drain(timeoutMs)` waits for in-flight cleanups.
    - `recordingBackgroundCleanupService.js`: slow background reconciliation of unregistered files (1 file per 10s). Exposes `buildQueue()`, `processOneQueueItem()`, intervals + initial delays.
    - `recordingEmergencyDiskService.js`: low-disk-space cleanup orchestration. Serializes `runEmergencyCheck` via internal in-flight flag.
    - `recordingDiskSpaceService.js`: cross-platform free-bytes reader behind injectable boundary.
    - `recordingCapacityService.js`: read-only "would this retention fit?" projection behind `GET /api/admin/recording-capacity`. Measures GB per camera-hour from `recording_segments` (span via SQL `julianday()`, because a bare `YYYY-MM-DD HH:MM:SS` parsed in JS is read as local time and skews by the offset), falling back to the production-measured 0.43 GB. Budgets retention **plus grace**, and subtracts `RECORDING_EMERGENCY_DISK_THRESHOLD_BYTES` from usable space — crossing that reserve triggers bulk deletion, so it is not room to plan with.
    - `recordingFileOperationService.js`: the only safe delete/quarantine side-effect boundary for recording files.
    - `recordingMaintenanceStateRepository.js`: maintenance run status persistence.
  - Scheduling, playback, assurance:
    - `recordingScheduler.js`: `register({ name, task, intervalMs, initialDelayMs })` + `start()` / `stop()` + per-task telemetry (`runCount`, `lastRunAt`, `lastDurationMs`, `lastError`). Recording facade does not own raw timer handles in production.
    - `recordingPlaybackService.js`: segment lookup / playback policy / `updateRecordingSettings` → reconciler. `getSegments` answers in two parts: a RANGE-SCOPED list (`?from=&to=`, ISO UTC bounds the caller built from its own local day) and a whole-span `coverage`. Both only for admin/token scopes — a public preview is defined by its minute limit, so a date range there could return an empty preview, and a coverage map of days it may not watch would publish our retention.
    - `rentalPlaybackAccessPolicy.js`: the ONLY opening in "non-community footage never reaches the public". `resolveOwnerScopeAccess` = `?scope=owner` for a paid RENTAL (deliberately refuses `owner_private` — an operator's own private camera is replayed through `?scope=admin`). `isOwnerIssuedTokenCamera` = the share-link rule, and the single definition of it: a 'selected' token whose issuer owns that camera and whose rental is still paid up. That predicate is what an operator's `owner_private` camera rides on for family access, and `playbackTokenCameraCatalog` calls the SAME function so the picker and the segment gate cannot disagree.
    - `playbackRangePolicy.js`: pure — `parsePlaybackRange` (query → ISO bounds), `intersectWithAccessWindow` (a 7-day token naming a date three weeks back still gets 7 days), `isWithinRange`.
    - `recordingCoverageRunsService.js`: the whole recorded span as contiguous RUNS merged from disk + Telegram archive (production: 14-84 runs against ~1,400 segments, ~20x smaller). This is what lets the list be narrowed to one day without the timeline losing the ability to show that another day has no footage. A null `recorded_until` is derived from the duration, never read as the epoch. Either source missing degrades to the other rather than to no bar at all.
    - `recordingAssuranceService.js`: read-only assurance snapshot and operator-facing degradation summary.
    - `recordingHealthDashboardService.js`: read-only observability aggregator. `getSnapshot()` composes scheduler telemetry, recovery queue/diagnostics, recording process counts, restart history, and storage into one payload with a derived `ok`/`warning`/`critical` status. Backs `GET /api/admin/recording-health`. Each section is computed defensively so one failure degrades to a fallback instead of failing the endpoint.
    - `recordingHealthAlertService.js`: edge-triggered Telegram alerts. `checkAndAlert()` reads the health snapshot and sends a monitoring-chat message only when the level transitions (ok ⇄ warning ⇄ critical) — no re-spam while a level holds. Registered as the `recording-health-alert` scheduler task in server.js; gated by `config.telegram.healthAlertsEnabled` + `isTelegramConfigured()`.
  - Invariants (apply to all changes):
    - Recovery: playback only reads validated final MP4 rows from `recording_segments`; pending/partial/tmp/corrupt/orphan files are retained through retention+grace and reconciled before deletion.
    - Cleanup: all destructive paths flow through `recordingCleanupService.js` + `recordingRetentionPolicy.js`. Pending `.mp4.partial` recovery files from unstable connectivity must not be terminal-quarantined by recovery before retention cleanup owns their deletion. Final `.mp4` orphans can be quarantined only after retry exhaustion and must receive a recovery/finalizer pass before permanent deletion. Pending partials are retried with backoff and retained until retention+grace expires. Emergency disk cleanup uses the same safe-delete boundary and may bypass retention only for DB-registered segments below the emergency target.
    - In-progress tracking: `recoveryService.isFileOwned()` is the single source of truth. Do not introduce parallel `Set`s in callers.
    - Concurrency cap: every recovery path (segment-close, scanner, cleanup orphan, background cleanup) must call `enqueueRecovery` — never bypass the queue.
    - Lifecycle transitions: external services (`cameraHealthService`, `recordingPlaybackService.updateRecordingSettings`, boot auto-start) call `reconcileRecordingLifecycle` only; `handleCameraBecame*` is internal to the reconciler.
    - Trace: retention skips logged with stable reason, filename, and age seconds for auditable NVR decisions.
- Viewer analytics:
  - `viewerSessionService.js`, `viewerAnalyticsService.js`: live viewer sessions/history/aggregation; session close accepts explicit end times from HLS proxy and stale cleanup.
  - `cameraViewStatsService.js`: compact per-camera lifetime live-view counters and active-viewer public card aggregates.
  - `playbackViewerSessionService.js`: playback viewer sessions/history/aggregation.
- Playback token entitlements:
  - `playbackTokenService.js`: token/session/share/audit orchestration, public activation, stable repeat-share access codes, initial and repeat selected-camera share text names/counts via one batched camera query, default-camera metadata for public auto-selection, transaction-scoped active-session limits, throttled session touches, and bounded token maintenance cleanup.
  - `playbackTokenRuleService.js`: normalized per-camera entitlement rules, selected/all scope evaluation, and effective playback window resolution.
  - `playbackCoverageService.js`: how far back footage can ACTUALLY be served — the shallowest camera's local retention versus the Telegram archive's real depth, whichever is deeper. Read-only, cached 60s. A stopped archive contributes 0 rather than its old depth: a gap longer than local retention is a HOLE, not a shorter window. `playbackProductService` annotates both catalogue lists with it so `window_hours` (a promise) is always shown beside the footage that exists (a fact).
  - `subscriberCameraPublishService.js`: the operator's ONE-WAY lever over a rented camera — `unpublishSubscriberCamera` takes it off the public hub and nothing here can put one on. Publishing a customer's camera is their consent to give and they already hold that switch in their own portal; unpublishing only ever removes exposure, which is the moderation an operator genuinely needs. Invalidates BOTH the list cache and the 30s live-access cache, or the stream stays openable to anyone holding the URL after the operator was told it was down. Refuses any class other than `subscriber`.
  - `playbackTokenCameraCatalog.js`: which cameras a validated token may be TOLD about, for the public viewer's camera picker. Exists because the public camera list is community-only, so an owner-issued link to a private camera rendered a picker with nothing in it. Answers only for `scope_type='selected'` and re-uses `rentalPlaybackAccessPolicy.isOwnerIssuedTokenCamera` rather than re-deriving the rule — a catalog that listed more than the segment gate serves would be an enumeration oracle for private cameras. Never takes a client-supplied filter.
  - `playback_token_camera_rules`: indexed token-camera rule table; selected tokens can explicitly grant `admin_only`, while all-scope tokens exclude `admin_only` unless an enabled rule exists.
- Public growth:
  - `publicGrowthService.js`: sanitized public area/discovery read models; normalize incoming area slugs/names before DB reads so frontend area links and older raw-name URLs resolve consistently.
  - `vehicleCountService.js`: public read model for the YOLO vehicle counter (opt-in via `VEHICLE_COUNT_CAMERA_ID` + `VEHICLE_COUNT_STATS_PATH`; empty by default, so other deployments see nothing). Reads the counter's JSON state file, never writes. Two rules it exists to enforce: the `camera_class='community'` gate still applies even if the counter is pointed elsewhere, and counts older than `VEHICLE_COUNT_STALE_AFTER_MS` are flagged `berhenti` so a stalled counter cannot keep showing its last total as live. Internal fields (model name, imgsz, frame counts, file paths) are deliberately dropped from the payload.
- Admin/settings/security:
  - `adminDashboardService.js`, `settingsService.js`, `brandingService.js`, `sponsorService.js`, `saweriaService.js`.
  - `promoBannerService.js` + `promoImageService.js`: the provider's OWN promo poster ("house" advertising), distinct from all three neighbours it is easy to confuse it with — `sponsorService.js` (third-party logos over the video), the Adsterra `ads_*` keys in `settingsService.js` (network ad code, switchable off — a promo banner keeps showing), and `promoService.js` (wallet top-up promo CODES, unrelated). `promoBannerService` resolves ONE banner per viewing context, most specific first (camera > area > all) then `priority`, filtered by schedule and placement, and aggregates impressions/clicks per day. `promoImageService` re-encodes uploads to WebP at 1200px + 640px with ffmpeg/libwebp (no `sharp` dependency) under `data/promos/`, served publicly at `/api/promo-media/` behind a filename allowlist.
  - `affiliateOfferService.js`: partner SHOPS and their product offers — the fifth commercial concept in this folder, so read the promo entry above before assuming which one you want. A partner is the commercial deal (`billing_mode` lifetime/term, `price_rupiah` INTEGER where **0 is valid** — the operator promotes their own shop free); an offer is the content (product title, description, product URL, targeting). Resolves ONE offer per viewing context using the same specificity ordering as the promo banner (camera > area > all, then `priority`), and the public payload is a hand-built SIX-key allow-list that never carries a camera name, a price, or the partner's raw URL — visitors only ever see this backend's own `/go` redirector. Liveness (offer active + partner active + schedule) is re-checked on the redirect path too, so deactivating a partner immediately kills their link.
  - `affiliateOfferExtras.js`: the pure helpers behind the three OPTIONAL parts of an offer — WhatsApp number/message normalising, the rupiah price (where **NULL means "hide the price" and 0 means "free"** — do not collapse them), and the 13-key public payload builder. Extracted purely so `affiliateOfferService.js` stays under the 800-line ratchet; it is re-exported from there, so no import path changes. Its template substitutes `{barang}` and `{toko}` ONLY — never `{kamera}`, because a camera name on a public payload is the exact leak the promo resolver shipped for months.
  - `authService.js`, `userService.js`, `apiKeyService.js`, password/session services, `securityAuditLogger.js`.
- Standalone-sidecar bridges (config for stacks that run OUTSIDE this app; no DB coupling, file-based, atomic tmp+rename writes so the sidecar can read concurrently):
  - `rondaConfigService.js`: per-camera settings for the Ronda Digital motion-detector containers under `RONDA_CONFIG_DIR`; also derives each detector's liveness from its `status.json`.
  - `telegramArchiveService.js`: routing rules for the `tg-archive` recording-upload sidecar under `TG_ARCHIVE_DIR` (which camera/area goes to which Telegram group), plus read-only reads of the sidecar's `state.db` for upload activity and a server-side `verifyChat` so the bot token never reaches the browser.
- Support utilities:
  - `thumbnailService.js`: background thumbnail stale queue, strict on-demand 3-hour thumbnail cadence, direct/on-demand generation, FFmpeg argument construction, failure backoff, and DB thumbnail metadata updates.
  - `thumbnailPathService.js`, `timezoneService.js`, `telegramService.js`, `backupService.js`, `discoveryService.js`.
  - `telegramService.js`: Telegram bot config, multi-target monitoring groups, area/camera/global routing rules, grouped camera status messages with per-camera detected timestamps, feedback messages. Also the single low-level outbound primitive `callTelegramApi(method,payload)` (reused by the interactive bot), the bot command allow-list (`commandChatIds`, fallback → monitoring chat) via `getBotRuntimeConfig`/`isCommandChat`.
  - `telegramBotService.js`: INTERACTIVE bot (two-way). Long-polls `getUpdates` (no webhook/public URL needed), drains backlog on start so stale taps aren't replayed, idle-rechecks every 15s until a token is configured. Routes /commands + inline-button callbacks for customer management: approve/reject registrations, /pending, /customers (paginated), /customer detail, /stats, /topup (confirm), suspend/resume, change plan. Authorization = `isCommandChat`. Mutations go through the same audited billing/wallet services as the web UI (synthetic `botRequest` attributes the actor). `notifyNewRegistration(userId)` pushes an approve/reject card to command chats (called by authController on signup). Lifecycle start/stop in server.js.
  - `telegramBotPresenter.js`: PURE presentation for the bot — `parseCommand`, `encodeCallback`/`decodeCallback` (versioned `t1:` prefix, <64B), rupiah/HTML formatting, and all message-text + inline-keyboard builders. No I/O; unit-tested directly.

## High-Risk Files

- `cameraHealthService.js`: very large and side-effect heavy. Extract only one responsibility at a time with focused tests.
- `cameraService.js`: mixes read models, writes, import/export, restore, and bulk policy. Prefer new pure helpers or repositories before adding branches.
- `recordingService.js`: facade only. Add new responsibility to a focused recording-domain module (see Recording domain above) and delegate; do not grow the facade.
- `securityAuditLogger.js`: avoid broad changes because many services depend on audit helpers.
- `settingsService.js`: settings affect frontend config, health, playback, ads, and branding.

## Cross-Service Side Effects

- Camera mutations may invalidate cache, write audit logs, update MediaMTX, update runtime/health state, and reconcile recording for recordable HLS delivery types (`internal_hls`, `external_hls`). RTSP URL, codec, delivery, enabled-state, external HLS URL, and internal RTSP transport changes must restart/start/stop FFmpeg automatically so operators do not need a manual disable/enable cycle. Live internal HLS source changes flow through `cameraSourceLifecycleService`, which sets reconnecting runtime state, refreshes the MediaMTX path lifecycle, clears per-camera health runtime caches, bumps `cameras.stream_revision`, and writes masked lifecycle events so stale active paths do not leave Camera Management stuck in reconnecting state. Internal RTSP transport and thumbnail strategy changes are opt-in and preserve existing behavior unless a camera override is set.
- Health transitions may update DB runtime state immediately, route grouped Telegram up/down notifications only after confirmation timing accepts a stable monitoring-state transition, include the original detected transition time per camera in Telegram messages, pause/resume recording, and influence thumbnail generation; runtime online signals and confirmed online transitions trigger recording lifecycle reconciliation so cameras that return after minutes or hours offline resume recording without manual toggles; public map/grid availability stays derived from camera availability state rather than Telegram alert routing, strict RTSP Telegram checks are opt-in for explicit internal camera policies/source profiles, RTSP transport remains governed by internal RTSP transport policy, and background thumbnail work must remain capped and stale-first to avoid bandwidth spikes on large camera fleets.
- Recording transitions may spawn/stop FFmpeg with explicit app-timezone `TZ`, write UTC segment rows from app-local filenames, quarantine/delete files, and write restart logs. Settings flip-to-disabled and delivery-type changes also stop active FFmpeg via the lifecycle reconciler's `stop_disabled`/`stop_unrecordable` actions — operators do not need to manually stop recording after toggling.
- Viewer session cleanup may move rows into history/archive tables and increment compact camera view counters; use the last heartbeat/HLS touch as the close time when available and keep live and playback flows separate.
- Settings updates may alter health cadence, playback policy, branding, ads, timezone, and notification behavior.

## Extraction Rules

- Prefer pure policy/helper extraction first, then service wiring.
- Keep old method signatures stable while moving internals.
- Add Header Docs to every new service/helper.
- Add or update focused tests next to existing `backend/__tests__` coverage.
- For DB work, inspect index coverage and use `transaction()` for grouped writes.
- Avoid importing route/controller modules into services.
- Migration runner hygiene: `../database/run-all-migrations.js` is import-safe, excludes aggregate scripts inside `database/migrations/`, and creates `../data/` before SQLite migration execution.
- Frontend helper boundary already present: map coordinate parsing lives in `../../frontend/src/utils/mapCoordinateUtils.js`; playback segment matching lives in `../../frontend/src/utils/playbackSegmentSelection.js`.
